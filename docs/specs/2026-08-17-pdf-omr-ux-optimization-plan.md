## 一、综合结论

两份报告结论一致且互补：

- **最大的问题是失败路径**：当前管线对真实乐谱 PDF 基本不可用（仓库自测 29/29 页 full-page 分割失败，干净矢量 PDF 也失败），而 UI 把失败吞成一句泛化文案 + 裸错误码，引导用户"重试"一个确定性失败。
- **过程反馈近乎缺失**：分钟级识别中主视口全空，管线实际在发结构化进度但未呈现；无阶段耗时、无 ETA。
- **信息密度两极**：关键信息（真实失败原因、页数、耗时、可用性 reason）缺失，同时低价值信息（40 位 hash、三引擎长段不可用原因）常驻占屏。

## 三、任务拆分

按可独立交付、可独立验证拆分。T1–T3 为第一波（改动集中、收益最大），T4–T7 为第二波，T8 为管线侧。

### T1 · 失败路径讲清楚（P0）

**范围**：F1 + F2 + F3 + F4
**改动点**：

- pipeline error context 透传：把 stage、真实 reason（segmentation 歧义、groupCount、页码）从 Main/pipeline 带到 snapshot error（注意 Bridge Zod schema 需同步）。
- `zh-CN` reason→文案映射扩容，每条给可操作建议（换引擎/换输入/降分辨率）。
- 失败框内"重试"降级为次级按钮，新增"更换引擎 / 重新选择输入"主操作。
- `stageState()` 增加"未执行/已跳过"态，失败后续阶段不再显示"等待"。
- 诊断徽章计入任务错误，或面板改名"校验诊断"并注明错误不在此计数。

**验证**：用 `olimpic …/6011095/input.pdf` 复现失败，确认真实原因可见、替代操作可用、后续阶段显示"已跳过"。

### T2 · 过程反馈落地（P0）

**范围**：P1a + P2a + P3a + S1
**改动点**：

- 主视口（中间证据区）运行中显示实时进度：当前单元（如"谱表系统 1/2"）、进度条、阶段耗时；管线已有结构化 progress，接出来即可。
- ETA：最近 N 个 tick 平均速率估算剩余时间。
- 阶段切换 toast / badge 变化；`progressBig` 降字号 + tabular-nums。
- 记录每阶段耗时与总耗时并在阶段列表展示。
- 状态芯片修复 ready 死文案：无 job 且已选文件时显示"可以开始 · {engine}"。

**验证**：`melody-clean.pdf` 成功路径全程观察进度/ETA/耗时；已选文件未开始时芯片显示"可以开始"。

### T3 · 原始输入预览（P0，需新 Bridge 能力）

**范围**：R1
**改动点**：

- 新增 Bridge API（request/response/capability/tests 四件套）：渲染输入 PDF 页面为缩略图作为 evidence 回传（Main 已有 pdfjs 渲染能力）。
- `web-core` schema 增加 evidence 类型。
- `PdfEvidence` "原始输入"标签页渲染第一页缩略图，理想可翻页。

**验证**：成功/失败后"原始输入"均能看到原谱页面。

### T4 · 状态与引擎披露（P1）

**范围**：S2 + S3 + S4 + S5 + F5
**改动点**：

- 状态 badge 升级为结果摘要卡：icon + 主标 + 副文（页数/时间）+ 下一动作推荐。
- 引擎可用性分 4 档（就绪/缺配置/runtime 不匹配/异常），渲染 reason + "在设置中配置"跳转；固定 reason→文案映射（预检失败保留原始 reason）。
- 下拉框 disabled 附原因说明（tooltip 或行尾文案）。
- 输入摘要展示 pageCount、页面尺寸、输入类型（inspect 产物入 UI）。

**验证**：三引擎不同不可用原因分别显示正确文案与跳转；已选 PDF 后展示页数。

### T5 · 布局与密度（P1）

**范围**：L1 + L2 + L3 + L4 + R3
**改动点**：

- 右栏只保留当前引擎一行状态，其余折叠或收回设置页。
- 三栏改 `320px 1fr 320px` 或右栏可折叠抽屉，保证中栏 ≥ 50vw。
- 导出按钮在 succeeded 时 sticky；成功/失败后加下一步引导（"继续识别下一份"/"换引擎重试"），显式说明导出位置、不入库。
- 阶段行加耗时、失败错误简码、完成后关键产出（"0 blocking / 2 warnings"）。

**验证**：1280px 宽度下中栏可读；导出按钮滚动中可见。

### T6 · 诊断语义与会话恢复（P1）

**范围**：S6 + S7 + R5 + S8
**改动点**：

- 导航返回后从 controller snapshot + input 摘要恢复完整会话状态（输入面板、导出状态）。
- 诊断：code→人类解释映射进 i18n，按 severity 排序，"展开全部" + N/M 计数，替换循环 placeholder。
- 选择文件失败区分原因（用户取消不报错/文件不可读/系统拒绝）。

**验证**：识别完成后离开再返回，页面状态完整；含 diagnostics 的样例显示语义化条目。

### T7 · 打磨项（P2，可合并进以上任务顺手做）

**范围**：L5 + L6 + P5a + R4 + S9 + R2 + P6a

- 文案统一"识谱引擎"、hash 截断前 8 位、"实验工具"措辞、校验语义说明。
- 状态图标化（引擎点 ✓/⚠/✗、阶段 accent 条、失败红边）。
- 取消中间态反馈。
- validate 阻塞 → 回退 recognize 的视觉提示。
- header 元信息行；对照预览 tab（依赖 T3）；引擎状态周期监测。

### T8 · 管线能力（与 UI 解耦，产品决策项）

**范围**：C1a + C2a

- 短期：inspect 后前置预判（已知必败的输入提前提示，UI 侧可并入 T1）。
- 中期：把 CLI 的 `--input-scope system-crop` / `--staff-layout` 暴露到桌面 UI（需要新 Bridge 参数面，单独设计）。
- 长期：修复 full-page 分割。

## 四、执行建议

- **第一波（一个 sprint）**：T1 + T2。改动集中在 `PdfOmrPage.tsx`、`packages/app-i18n`、pipeline error context 三处，直接解决"失败讲不清 + 过程看不见"两个 P0 主题。
- **第二波**：T3（Bridge 能力，需独立排期）→ T4 → T5 → T6。
- T7 打磨项不单独排期，拆进相关任务顺手完成。
- T8 需要产品决策，UI 侧先做"前置预判提示"即可，不阻塞 T1。
